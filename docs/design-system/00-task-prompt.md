# Task: Design a design system for Les Canetons (learning session)

> The original brief, saved verbatim so a new session has it. See `HANDOVER.md` for where the work stands.

You are a senior frontend architect and my mentor. I want to build a design system for the Les Canetons website. I know the overhead is too big for a one-person project; the real goal is **learning clean architecture** by doing it properly. So optimize for clarity of reasoning and good boundaries, and explain the *why* behind every decision, not just the *what*.

## Ground rules

- Work in phases and **stop at every checkpoint** for my decision. Don't jump ahead.
- Phases 1–3 are analysis only: read code, write docs, no changes to application code.
- When you implement (Phase 5+), work on a feature branch, in small commits with clear messages. Don't push or open PRs without asking.
- Verify current versions and compatibility of every tool you propose (React 19, TypeScript 6, Vite 8, Tailwind 4) instead of relying on memory.
- When you introduce a concept (dependency rule, public API, semver, tokens, etc.), explain it briefly and link one good source for further reading.

## Context

Monorepo-ish repo with two apps served from the same origin:

- **`web/`**: React 19, TypeScript 6, Vite 8, Tailwind CSS 4 (CSS-first, tokens in the `@theme` block of `web/src/styles.css`, no `tailwind.config.ts`), Radix UI, lucide-react, sonner, class-variance-authority + clsx + tailwind-merge, React Router 7, react-hook-form + zod, TanStack Query hooks generated by orval, i18next (FR at `/`, DE under `/de/`), MSW for `dev:mock`, e2e and PR previews, fonts Karla and Bungee via Fontsource.
- **`api/`**: Laravel 13, PHP 8.4. Not relevant for the design system except as the source of data shapes.
- **Tooling**: Vitest + Testing Library, Playwright + axe-core, Lighthouse budget, ESLint (typescript-eslint), Stylelint, Prettier, Husky + lint-staged.
- **Delivery**: merge to `main` deploys to TEST via a custom FTP tool; QA/PROD via tagged GitHub workflow; PR previews on GitHub Pages against MSW.

If `docs/ux-review/` exists or the repo has a "UI/UX Improvements" milestone (`gh api repos/{owner}/{repo}/milestones`), use its component inventory and findings as input. They came from a black-box UX review; now you get to compare them with the code.

## Phase 1: Analyse the current state

Read the frontend code and document in `docs/design-system/01-current-state.md`:

1. **Tokens**: everything in `@theme`, plus every value that escapes it (arbitrary Tailwind values like `bg-[#…]`, hex/rgb in TSX/CSS, inline `style` props). Group by category: color, typography, spacing, radius, shadow, motion, breakpoints, z-index.
2. **Components**: every component in `web/src`, classified as *presentational* / *feature/container* / *mixed* (candidate for splitting).
3. **Dependency graph**: which components import what. Use `dependency-cruiser` or `madge`, and highlight where UI components depend on things a design system must not know (orval hooks, TanStack Query, React Router, i18next, zod schemas, MSW).
4. **Duplication and drift**: components or class strings that do the same thing in different ways; `cva` variants that overlap.
5. **Existing build setup**: root and `web/` `package.json`, whether npm workspaces are already used, tsconfig project references, path aliases, Vite and Tailwind setup.
6. Compare with the UX review inventory if it exists: which candidates already exist in code, partially exist, or are new.

## Phase 2: Target architecture (independent of where the code lives)

Write `docs/design-system/02-architecture.md`: layers (tokens → primitives → composites → patterns/layouts → app features), the dependency rule (what the design system may and may not depend on; how text, links and data are passed in), public API and how it is enforced, token format (Tailwind 4 `@theme` CSS vs DTCG JSON + Style Dictionary), theming, component contract (props, `cva` variants, `className` merging, React 19 `ref`, accessibility guarantees, states: default, hover, focus-visible, disabled, loading, error), and enforcement (`eslint-plugin-boundaries`, `dependency-cruiser` in CI, TypeScript project references).

## Phase 3: Compare distribution approaches

Write `docs/design-system/03-approaches.md` for: (1) in-app module with `@ds` alias, (2) workspace package, source-only, (3) workspace package, built (Changesets), (4) separate repo + published package, (5) copy-in registry (shadcn-style); plus hybrids. For each: folder structure, consumption, build and release, how Tailwind 4 picks up classes (`@source`), tokens and fonts, testing and documentation, CI/deploy impact, what you learn. Provide a comparison matrix, a migration path, and a recommendation (lead with an opinion). Also propose the documentation/playground tool (Storybook, Ladle, in-app `/dev/components`) and the testing strategy (Vitest + Testing Library, axe, visual regression), with trade-offs.

### ✋ Checkpoint 1

Stop and summarize Phases 1–3 in a short message: key findings, the recommended approach, and the open decisions. Wait for my choice.

## Phase 4: Architecture Decision Records

After I decide, write ADRs in `docs/design-system/adr/` (Context, Decision, Alternatives considered, Consequences) for at least: distribution approach; token source of truth and format; boundaries and how they're enforced; documentation/playground tool; testing strategy; versioning (or why there is none).

## Phase 5: Vertical slice

Implement the smallest slice that proves the architecture end to end:

- Token layer with the semantic tokens actually used
- Two primitives (`Button`, `Input`) and one composite (`FormField` with label, hint and error)
- Boundary enforcement running in lint/CI
- Documentation entries in the chosen playground, including all variants and states
- Tests: unit + a11y for each component
- Migrate **one real screen** (pick the one with the most drift from Phase 1) to the new components, with no visual regressions except intentional fixes
- CI, `dev:mock`, PR previews and the FTP deploy build must still work

### ✋ Checkpoint 2

Stop and show me the diff summary, what went well, what felt like friction, and what you'd change in the architecture before scaling it. Wait for my go.

## Phase 6: Roadmap

Write `docs/design-system/04-roadmap.md`: the order in which to build the remaining components (dependency-ordered, primitives first) and migrate screens, with an effort estimate per step. If the UX review milestone exists, map roadmap items to its issues instead of duplicating them, and propose new issues only for gaps. Don't create GitHub issues without asking.

## Learning wrap-up

At the end, write `docs/design-system/05-learnings.md`: the clean-architecture principles we applied, where they paid off, where they were overkill for this project size, and what I should try differently in a larger, multi-team setting.
